Creating a room changes Better IAM: the room is registered as a resource, its creator gets the `owner` relation, and a
key is created for its files. Inviting someone adds them to a group or sends an invitation. These are **identity-system
writes**, and Better Files makes them only after it has authorized the caller for the data room operation.

The question is whose credential makes them. If it were the caller's, every room owner would need permission to edit
Better IAM's resources, relationships and keys directly, which is far more than inviting someone to a room should
need. So Better Files uses a **system credential** instead: an API key of a service account in each tenant, allowed
exactly the actions it needs.

```ts
betterIamIntegration(iam, {
  iamPlugin,
  systemCredential: (tenantId) => ({ token: serviceKeys.get(tenantId) }),
});
```

`systemCredential` receives the tenant id and returns a credential (`{ token }` or `{ headers }`), or a promise of
one. The same credential is used for KMS calls, which also happen outside any request: serving a download ticket,
or running `dr.maintain()`.

<Callout type="warn" title="Without a system credential">
  Writes use the caller's own credential, which then needs the actions below in Better IAM. Better IAM's KMS is not
  offered for files either, so `betterFiles()` needs `encryption: { keys }` of its own, or refuses to start.
</Callout>

## The permissions it needs

`systemPolicy(iam)` returns the policy document for the service account's role. Pass the Better IAM instance: the
document then names only the actions that release knows. Better IAM 0.2.x refuses a role that names the guest actions it does not have.
After upgrading to 0.3, update the role's document with the new output, which adds the guest actions.

| Group | Actions | Used for |
| --- | --- | --- |
| Resources | `iam:resources:create`, `read`, `update`, `delete` | Registering rooms and keeping their attributes current |
| Relationships | `iam:relationships:create`, `read`, `delete` | Room roles |
| Groups | `iam:groups:create`, `read`, `update`, `delete` | Permission groups and their members |
| Roles and bindings | `iam:roles:create`, `read`, `iam:bindings:create` | The participant role, bound to everyone given a room role |
| Identities | `iam:identities:read`, `create`, `update` | Finding people by email; member invitations for outsiders, and withdrawing them |
| Guests | `iam:guests:invite`, `iam:guests:manage` | Guest invitations, and withdrawing them (only on releases with guests) |
| Keys | `iam:kms:create`, `update`, `generate-data-key`, `decrypt`, `delete` | A key per room, data keys for files, destroying a deleted room's key |

All of them are allowed on `iam/*`, the tenant's own platform resources.

## Creating it

Do this once per tenant, for example when you onboard an organization, as an administrator of that tenant:

```ts
import { systemPolicy } from 'better-files/iam';

const account = await iam.api.serviceAccounts.create(admin, {
  tenantId,
  name: 'Better Files',
  description: 'Registers rooms, room roles, groups and keys for data rooms',
});
const role = await iam.api.roles.create(admin, {
  tenantId,
  name: 'Better Files system',
  document: systemPolicy(iam),
});
await iam.api.bindings.create(admin, {
  tenantId,
  roleId: role.id,
  subjectType: 'identity',
  subjectId: account.id,
});
const key = await iam.api.credentials.create(admin, {
  tenantId,
  identityId: account.id,
  name: 'better-files',
});
// key.token is returned once: store it in your secret store, keyed by tenant.
```

API keys expire. Rotate them by issuing a new key, storing it, and revoking the old one with
`iam.api.credentials.revoke`; `systemCredential` is called on every write, so a new key takes effect immediately.

<Callout type="idea" title="Bounded by the issuer">
  Better IAM issues a key only within the issuer's own grant authority. The administrator creating the key must be
  able to grant everything in `systemPolicy(iam)`.
</Callout>
